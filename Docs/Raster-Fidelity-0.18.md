# 0.18 图像保真修正

日期：2026-10-29。三项问题均在本机复核，按独立实现修复。原书只读，实样、截图和参考软件不分发。

## 1. 原始像素与DPI

DjVuLibre的`-scale=100`表示按100DPI显示，不是百分之百像素。此前300DPI、512×640的生成页被输出为170×212；前次检查只看成败、页数和部分渲染，未核对原始像素，因而漏检。本版改用`-subsample=1`。主阅读、OCR、转换、缩略图与多页预览共用此路径；窗口缩放与源图像像素分开。

转换额外保留DjVu INFO中的DPI，以正确确定纸张尺寸。单页内嵌DjVu直接读INFO；多页文档使用随包djvused的页信息。生成150、300、600DPI页分别检查PDF内图像尺寸和MediaBox，未知DPI才使用回退值。

## 2. JPEG图层与失败结果

旧版组件以`--without-jpeg`构建；生成的BGjp照片页返回退出码0、512×640全白且无诊断。本版静态链接IJG JPEG 10，启用JPEG背景及前景图层。源码、许可与本地DjVuLibre补丁随包提供，运行不依赖Homebrew。

不以“全白”推断失败，合法白页保留。BG2k、FG2k及目前不支持的CMYK JPEG图层明确失败，避免静默忽略图层；解码诊断也不再被当作成功。页面INFO和JPEG图层在位图分配前检查30000边长、6000万像素上限，子进程有超时、强制回收和输出上限。构建指纹防止继续打包未启用JPEG的旧缓存组件。

还确认了直接JPEG码流的同类问题：仅凭头部宽高即可把截断文件写入PDF，ImageIO也可能容错后报告完整。现在沿JPEG段边界核对主扫描的结束标记，跳过EXIF等段内缩略图，再实际解码并检查ImageIO完整状态；失败不提交PDF。标准JPEG、TIFF的EXIF方向用于阅读和OCR，转换只应用一次方向矩阵，不再重复解码已规范化的照片页。

## 3. 超星照片页的判定边界

规则参考阿虚提供的2026-10-29全平台源码快照及其《0.2.2-超星彩色DjVu方向与手机实测》：只有从V2 PDG容器解出的纯BG44照片页使用DIB行序和通道还原。此处由本项目独立编写Swift解析及像素处理，没有复制阿虚实现或Windows解码器。

判定同时检查来源和图层：必须为HH V2；DjVu必须是单页FORM:DJVU，具有INFO与BG44，且无JB2掩码、前景、调色板、共享字典或其他图像图层。直接DjVu或只改名为.pdg的文件、V1、黑白及复合页保持标准解释。修正在逻辑上先于INFO旋转；四种页面方向均验证。灰度照片仅还原行序，这一推断经生成夹具验证，仍缺实书灰度样本。

上游固定提交`aa6f00258534e537f1be06223fb4aee2772e3546`中的000041.pdg与对应原版DLL渲染BMP仅作本机比较。原始DjVu页752×1088，参考渲染2336×3264；将参考对齐原生尺寸后，RGB平均绝对差约0.25/0.25/0.25。原始像素不为模仿参考软件的放大而重采样。文件本身不放入本项目或发行文件。

## 4. 验证与复现

`Tests/test_raster_fidelity.py`生成JPEG、IW44、JB2、复合图层、V1/V2容器、旋转、DPI及损坏输入。检查独立解码色块、标准文件不误修正、UVZ路径、PDF像素与纸张尺寸、失败原子性及14种EXIF方向状态。c44/cjb2等生成工具只留在本地构建缓存，不随应用分发。
